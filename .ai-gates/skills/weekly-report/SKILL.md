# 周报

首行：**`[weekly]`**。日常入口：[agent-entry-route.md](../references/agent-entry-route.md)；争议/recovery：[CORE.md](../CORE.md)

## 触发

用户说「周报」时启用；不参与 Express/Direct/Standard/Full 路由。用户借「周报」顺带提代码/README 改动需求时，不在本岗处理——须另起一条先 `[PM]` 判车道（硬门禁 #7）。

## 模型路由 + 子窗

本岗**不要求子窗**：用户单独说「周报」时在当前窗直接做即可；不纳入流水线「主窗仅 PM / 全岗子窗」派发。细则 → [model-routing.md](../references/model-routing.md) §周报例外。

## 用途与读者（强制）

- 产出是**用户拿去向别人汇报**的正文，不是 Agent 向用户汇报、也不是技术复盘稿
- 读者默认是**不懂程序、不熟悉本项目**的同事
- 目标：听完/看完能立刻明白「这周做了哪些事、做到哪一步」
- 语气：正式汇报用语；**禁止**过度口语化；**禁止**项目黑话与内部编号
- **人与 AI 工作合一**：正文只写「本周完成了什么 / 验证到哪一步」，**禁止**拆成人做的、AI 做的、程序员/审核/人测分项；状态用「已落地 / 已验证 / 已结案 / 尚待最终确认」，不用「人测通过」「代码审核通过」「AI 实现」等分工说法

## Checklist

1. **文档路径**与**日期区间**至少一项；都缺则向用户索取
2. 默认**只输出正文**，不改执行文档/README/代码
3. 正文不出现路径、文件名、skill 内部用语、方案窗名、版本号、内部切片/热修编号
4. 本周只写材料支撑的工作；`Unity` 写作「引擎」
5. 用户要求「保存到文件」时才写入；默认 `.ai-gates/Doc/Weekly/`
6. 标题固定 `# 工作周报`；章节层级**不得改名、不得增删、不得换成汇报稿/口播稿等其他骨架**
7. 用户提供往期周报或格式样例时，优先对齐其详细度与用词习惯，但**不得破坏下方固定结构**
8. 材料较多时按独立工作线覆盖重点，通常整理 5～7 项详细进展（材料不足不凑数）；每项只附一段、通常 2 句
9. 严格区分「已完成规则调整」「已验证通过」「已结案」「进行中 / 待最终确认」；不把方案通过或代码落地写成终验已过
10. 下周工作通常整理 3～4 项；每项写清执行内容与验收标准
11. **只写工作内容与结果，不写 bug 故事**（见下节）

## 写法要素（对齐定稿口径）

### 写什么

- 用「完成了什么能力 / 做了哪类控制与排查 / 验证与结案状态」表述
- 主题标题写成工作名或能力名，例如「开管加热场景下的液体驱动控制」
- 未闭环项可写「进行中」「尚待最终确认」及边界，仍用工作内容语气

### 不写什么

- **禁止**「原问题 / 以前会… / 修好了…」等缺陷叙述
- **禁止**根因分析、调用链、日志键、API、文件与目录
- **禁止**口语聊天腔（如「乱跟着动」「猛灌」「还在做」）
- **禁止**项目内部叫法（如切片号、热修刀名、闸门/旁路等实现黑话）；须译成现象层或能力层白话
- **禁止**把工作拆成「人 / AI / 程序员 / 审核 / 人测」分工叙事；验证结论直接写能力状态，不写谁测的

### 状态用词（推荐）

| 材料事实 | 正文可用 |
| --- | --- |
| runtime / 用户验收通过且结案 | 已验证通过并结案 |
| 规则已落地、引擎未终验 | 规则已调整；尚待最终确认 |
| 主目标过、残留另记 | 主目标已验证通过；…已单独记录 / 已拆分排队 |
| 交其他模块 | 交由××侧继续跟进 |

## 输入模式

| 模式 | 材料 |
| --- | --- |
| 仅文档 | 执行文档 Step 进度 + 完成标准 |
| 仅日期 | README 版本记录按区间筛选 |
| 合并 | 二者兼有 |

## 正文结构（固定 · 不得改）

默认且唯一默认骨架如下（标题与层级文字须一致）：

```markdown
# 工作周报

**周期：YYYY年M月D日—M月D日**

## 本周工作

### 一、本周工作概要
[1 段、通常 2～3 句：本周主线能力、已结案范围、仍未闭环边界]

### 二、详细工作进展

#### 1. [工作/能力主题]
[1 段、通常 2 句：第 1 句写完成了什么；第 2 句写验证/结案状态或剩余边界]

#### 2. [工作/能力主题]
[同上]

## 下周工作

### 一、下周工作概要
[1 段、通常 2 句：下一阶段主线、收尾目标、回归范围]

### 二、下周详细工作内容

#### 1. [计划主题]
[1 段、通常 2 句：第 1 句写执行内容；第 2 句写验收标准]

#### 2. [计划主题]
[同上]
```

整理规则：

1. 按独立工作线拆项；同线内的连续完善可归入一项，但完成状态不得含糊
2. 每项只写一段；优先「完成内容 → 验证/结案或边界」，不写缺陷前后对比
3. 场景与结果须译成非项目同事可懂的表述；无材料支撑的细节不臆造
4. 下周只取材料明确记载的下一步、待确认项与排队事项，不凭空扩范围
5. 若用户明确要求简版，才改为「本周完成 / 验证与风险 / 下周计划」三段式；**未要求时必须用上方固定结构**
6. 若用户要求口播稿/PPT 提纲等，须**另附**，不得替换本固定周报骨架

## 禁止

- 写「本 skill」/ 内部岗位名 / 执行文档章节名直接出现在正文
- 把周报改成「汇报稿」「各位好」开场、或打乱上述章节名
- 以修 bug 叙事代替工作内容叙事
- 将人与 AI（或审核、人测）工作分开表述

## 定稿要素速查（生成前自检）

1. 结构是否仍是：本周工作（概要 + 详细进展）/ 下周工作（概要 + 详细工作内容）
2. 是否只写工作内容，未写 bug
3. 非程序同事能否一眼听懂做了啥
4. 语气是否正式、非口语
5. 完成/验证/结案/待确认是否分开、未夸大
6. 是否未拆分人与 AI / 审核 / 人测分工

详细字段说明 → [references/retrospective-metrics.md](../references/retrospective-metrics.md)
