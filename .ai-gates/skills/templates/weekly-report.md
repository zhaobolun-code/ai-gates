# 周报定稿（模板）

> 岗入口：`weekly-report/SKILL.md`。本页是定稿细则；触发口令「周报」；「日报」且要求同口径见文末 §日报。

## 用途与读者（强制）

- 产出是**用户拿去向别人做正式汇报**的正文，不是 Agent 向用户汇报、也不是技术复盘稿
- **叙述视角**：懂实现、对上级和同事汇报——像**由开发岗位转入项目管理**的负责人：写交付内容与规则改动，不写岗位分工，不写材料从哪来
- 读者含**非开发同事**；正文须**书面、正式**，既不过度口语，也不过度幼稚化；专业词用**业务语言**（规则、路径、模块域、构建、单元测试、运行场景），**禁止**类名、接口名、行号、文件路径、内部编号
- **人与 AI 工作合一**：禁止拆成「人做的 / AI 做的 / 程序员 / 审核 / 人测」

## 写什么（取材 → 正文）

| 材料里有什么 | 正文应写什么 |
| --- | --- |
| Step 改码、Mandatory、implement-report | **程序能力与规则**：停用/调整/保留了什么行为（译成实验里能理解的表述） |
| Discover-only、方案审、文档修订 | **默认不进「本周详细进展」**，除非用户明确要求写文档工作 |
| 编译、EditMode、Unity、黄金回归 | 仅当**本周确实执行过**且属于交付动作时，可单列一项（如「完成命令行编译与自动化单元测试」）；**禁止**用门禁表罗列「未跑 / 待验」 |
| 人测红、blocked、进行中 | **禁止**写入「本周工作」；不得写现象、根因、对比前后 |

## 「本周工作」专用规则（强制）

1. **只写本周做了什么**（完成了哪些改动、完成了哪些验证动作）
2. **禁止写当前状态**：不得出现「待验证、尚未、未完成、进行中、未闭环、未测、仍属在研、现象仍是、后续需、留待下一刀」等
3. **禁止写缺陷与验收结论**：不写 bug 故事、不写「能不能用」的最终判断、不写「不等于场景通过」类免责声明（这些若用户要，另开复盘，不进周报）
4. **正文条目不写具体日期**：仅标题下 **周期：YYYY年M月D日—M月D日** 一行；详细进展标题与正文**不得**再写「9 月 10 日」等
5. 概要段同样**只概括本周完成事项**，不写「仍未…」类边界句（边界放到「下周工作」用计划与验收标准表达）
6. **五向专业叙述**（强制，见下节）：本周工作正文按「查到 → 增加 → 删除 → 改动 → 优化」铺开；**禁止**把这五个词写成小标题或分项标题

## 五向专业叙述（本周工作 / 今日工作）

内部取材按五向归类，对外写成连贯书面段，**不出现**「查到了什么 / 增加了什么」等标签。顺序固定：

1. **查到**：本周已做的核对、场景对照、编译与单元测试等验证动作（只写做了哪些核对，不写测红、根因、毫升现象）
2. **增加**：新登记项、新规则、新诊断字段、新启动的改动（写成模块能力，不写类名）
3. **删除**：停用或去掉的并行规则、重复通道、旧入口
4. **改动**：通断许可、验收口径、路径接到何处等规则调整
5. **优化**：同一类问题收拢后的行为改善（如不再被并行规则占额度），仍只写完成的优化，不写「尚未」

扩写要求：

- 用完整句子写清**完成了哪个模块、做了什么改动、优化了哪条逻辑**；不要压成口号或流水账
- **只写做了什么**，不写怎么想、不写为何如此、不写策略讨论
- 每条工作线通常 **一段、4～8 句**；材料少则短、禁止为凑五向而臆造
- 五向可落在概要（总括）+ 详细进展（按工作线拆段）；详细进展标题仍用**能力或规则名**，不用五向当标题

## Checklist（定稿）

1. **文档路径**与**日期区间**至少一项；都缺则向用户索取
2. 默认**只输出正文**，不改执行文档/README/代码（**改本 SKILL 须先写 `.ai-gates/CHANGELOG.md` 再改文件**）
3. 正文不出现路径、文件名、skill 内部用语、方案窗名、版本号、内部切片/热修/刀次编号
4. 本周只写材料支撑的**已发生工作**；无材料不臆造
5. 用户要求「保存到文件」时才写入；默认 `.ai-gates/Doc/Weekly/`
6. 标题固定 `# 工作周报`；章节层级**不得改名、不得增删、不得换成汇报稿/口播稿等其他骨架**
7. 用户提供往期周报或格式样例时，优先对齐其详细度与用词习惯，但**不得破坏下方固定结构**
8. 材料较多时按独立工作线拆项，通常 **5～7** 项（不足不凑数）；每项**一段**，按五向扩写专业叙述，只写完成内容
9. **下周工作**通常 **3～4** 项；可写计划与**验收标准**（面向将要做的验证，不是本周状态）
10. **只写工作内容，不写 bug 故事**
11. 黑话须翻译（见下表）；**禁止**未翻译的内部叫法入正文

## 写法要素

### 主题与句式

- 标题用**能力或规则名**（书面）：如「满管后传递路径与相邻导管对齐」「接近满液整段自动推进统一下线」
- 每条进展：五向顺序 + **动词完成式**——核对、增加、删除、调整、停用、完成（仅指本周已做）
- 概要：本周主线 + 五向总括，扩写成 **一段、约 4～8 句**，不要压成两句口号

### 黑话 → 正文（须翻译，禁止原文入正文）

| 材料里常见黑话 | 正文应写成 |
| --- | --- |
| hop / Register / STM / Kind / DryOpen | 气体或液体传递；导管两端相态；通断与传液依据 |
| 闸门 / 传感器唯一主人 / 并行主人 | 导管两端通断规则；唯一依据；与之并行的遗留规则 |
| #if false / REMOVED / 调用边 | 停用（某路径上的）自动触发 / 遗留逻辑 |
| 活塞 / 净帽 / 余隙 / Boyle | 随液体推动带走气体；气体让出空间；体积随气体量变化 |
| 止损 / 换层 / 热修 / 第 N 刀 / Rxx | **不写编号**；改写为具体规则或能力名 |
| runtime-validated / 人测 / CR / 方案审 | **不进正文**（除非用户明确要求写流程） |
| 结合 Git / 推送记录 / README 版本 | **禁止入正文** |

翻译原则：写**规则与实验行为**，不写**代码机制名**；语气**书面**，避免「掐住、走线、抢控制」等口语，可用「并行生效、中断推进、第二套规则」等。

### 不写什么

- 原问题、以前会怎样、修好了什么
- 根因分析、调用链、日志键、API、类名、物体实例号
- 口语聊天腔
- 人与 AI / 岗位分工
- 材料来源元话术
- **怎么想**：根因推断、策略讨论、「核对后确认是因为」
- **本周工作中的**状态、风险、里程碑表（除非用户明确要求「含状态版」，默认不用）

## 输入模式

| 模式 | 材料 |
| --- | --- |
| 仅文档 | 执行文档 Step 进度 + 完成标准（**只提取已落地改码与已做验证**） |
| 仅日期 | README 版本记录按区间筛选 |
| 合并 | 二者兼有；可对照 Git 提交**仅内部取材**，正文不写取材过程 |

用户指定「程序员周报 / 项目经理视角」时，仍遵守：**不写代码名、本周只写做了什么**；可略增「改动范围、主项与排队项」等管理表述，**禁止**回到接口级清单。

## 正文结构（固定 · 不得改）

```markdown
# 工作周报

**周期：YYYY年M月D日—M月D日**

## 本周工作

### 一、本周工作概要
[1 段扩写：本周主线 + 五向总括，仅完成项，无五向标签]

### 二、详细工作进展

#### 1. [工作/能力主题]
[1 段扩写：本周完成了什么]

#### 2. [工作/能力主题]
[同上]

## 下周工作

### 一、下周工作概要
[1 段、2 句：下一阶段主线与范围控制]

### 二、下周详细工作内容

#### 1. [计划主题]
[1 段：执行内容 + 验收标准（可判定）]

#### 2. [计划主题]
[同上]
```

整理规则：

1. 按独立工作线拆项；同线连续改码可合并一项
2. 「下周」只取材料中的下一步与排队项，不凭空扩范围
3. 用户要求简版时，才改为「本周完成 / 下周计划」两段式；**未要求时必须用上方固定结构**
4. 口播稿 / PPT 须**另附**，不得替换骨架

## 禁止

- 写「本 skill」/ 执行文档章节名于正文
- 「各位好」开场或改掉章节名
- 以修 bug 叙事代替工作叙事
- 本周段写状态、现象、未完成任务
- 正文黑话与取材元话术
- 五向标签当小标题；口号体；流水账；怎么想

## 定稿自检

1. 结构是否为：本周（概要 + 详细进展）/ 下周（概要 + 详细内容）
2. **本周是否只写「做了什么」**（出现待验/未完成/现象 → 未通过）
3. 条目内是否**无具体日期**（除周期一行）
4. 是否**无类名、路径、刀次、R 编号**
5. 语气是否**书面**且外行能懂「做了哪些规则/能力改动」
6. 是否未拆分人与 AI / 岗位
7. 是否未写 Git/文档取材过程
8. 是否以**改码与规则**为主，而非文档维护堆砌
9. 本周工作是否按「查到→增加→删除→改动→优化」铺开，且**没有**把这五个词当小标题
10. 是否扩写专业叙述（完成模块 / 改动 / 优化逻辑），而非口号或流水账；是否只写做了什么、未写怎么想

## 合格示例（摘要 · 本周段）

> 本周围绕气压驱动下的导管液体传递开展改造。完成拦截记录与场景对照，以及命令行编译与单元测试。在传递拦截记录中增加发送端与接收端各自剩余容量的登记，使两侧占用可分开核对。删除重复并行的诊断通道，并删除气体传递中仍在决定液体能否通过的旧入口。气体成功离开后不再扣减导管可传额度；传送许可改由管口是否允许通过来决定。同一时刻气体与液体争用额度时，液体不再被排气提前占尽可传额度。

## 反例（禁止）

- 堆 `hop/Kind/PressureController.cs:389/第三十七刀`
- 「Unity 未跑、A7 仍红、邻管 0.08 ml、待最终确认」
- 「结合仓库推送记录整理如下」
- 本周概要写「发送侧接液**尚未验收**」（应移到下周计划 + 验收标准，或删除）
- 把「查到 / 增加 / 删除 / 改动 / 优化」写成小标题或分项标题
- 压成口号、或按实验轮次记流水账、或写「核对后确认根因是…」类怎么想

## 日报（同口径 · 用户点名时）

用户说「日报」且要求按周报口径时，骨架改为：

```markdown
# 工作日报

**日期：YYYY年M月D日**  
**主题：[能力或规则名]**

## 今日工作
[一段或多段：五向专业叙述，无小标题]
```

- **无「下周工作」**，除非用户点名要明日计划
- 今日工作**允许写该日日期**（仅标题下日期行）；正文仍不写早午晚时段
- 其余强制规则与周报「本周工作」相同：只写做了什么、扩写、禁黑话、禁现象、禁怎么想
