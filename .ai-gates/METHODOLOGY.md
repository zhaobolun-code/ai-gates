# AI 辅助复杂系统开发方法论

想弄清「为什么这样设计」时再看本文。动手改代码、第一次接入仓库 → [USER-GUIDE.md](./USER-GUIDE.md)。护栏机制全表见本文 §3.5。版本见 [VERSION](skills/VERSION)。

本文给人读。助手日常从 README 与 USER-GUIDE 开工即可，不必把全文贴进对话。

## 摘要

用 AI 改复杂系统时，卡住的原因往往是：范围说不清、过关标准事后才补、同一条错路改很多轮、机器检查绿了就被当成现场已经好了。本文主张：在代码补全与审查之外，再管一层**开发流程的秩序**——事先写清改什么、怎样算过关；按改动规模走不同粗细的步骤；失败反复出现时停下来换思路；验收权留在人看见的现象上。**犯错不可怕，可怕的是一直犯同一个错误**（通用典故 **一错不二犯**）。错题本记坑，典故记已经验证过的结构，下次写方案前先扫一遍。

这套约定已经在仿真业务、流程自改、同事其他主题、另一光学仓库，以及非技术角色按口令推进的小游戏上用过，并且能做完收尾。它是一份使用记录：在这些项目里按约定做过、收得了尾。拿它判断「流程能跑完」；要比较「换一套约定会不会更好」，需要另外设计对照。

思考碰撞是点名才开的加审：用不同模型先对齐前提，再一轮「盖」对「拆」。四次实测里，新手续能跑通，写回后还能挖洞；未审过的流程稿、以及一份正在执行的业务实现，第一次碰撞也会打到同类问题（失败句抓不到、字段未钉、验收与清单不同句、机器绿与人看见的现象各说各的）。花费大约是普通方案审的两到三倍。日常开工仍走普通方案审，因为碰撞贵，而且模型并不会因此学会「我不知道」。元认知要靠把「假设了什么、不知道什么、定级凭什么」写进日常检查。

逆链是点名才开的倒走：从失败标准和「不选的」往回看设计连没连上。有一次归档演练，又对同一份模拟切片做了同稿异模型并联两次，再对一份改码前业务方案先倒走（停在启用手续），补完行数与逐条代价后再倒走一次：手续合格后设计连接撑住。标通过须完成抽检。这是演练记录，用来决定倒走前先把启用手续做完。

分歧标注是点名才开的多视角：同一轮先各自写推理链再对照。对同一份模拟切片跑了一次，打到一条真实分歧（本步零行为与总现象失败标准连不连得上），两边都同意本步只诊断、不去改当时实现。花费低于一次逆链倒走加抽检，也低于一次思考碰撞。现行做法是两个隔离槽、对照由派发方写。日常仍走普通方案审。

项目典故是日常检查：写方案前扫设计模式症状表。三次跨仓库实测（新对话、玩法不写模式名）：一次按触发症状对上词条并按结构落地；一次扫到词条后按禁用边界改走直调；一次在 **使用与入表拆开** 之后对上词条并按配方新建（该仓当时没有可复用的验证入口）。三次都是人看见现象后签收。拿它判断「症状表能把玩法翻成可执行选型」。漏接线要在交审时核调用点：新文件在磁盘上，还要接到成功路径，人才能看见效果。

外仓对照是点名才开：先读本仓库，再短清单公开仓，浅克隆到临时目录只抽结构，禁止把外仓代码拷进业务目录。一次实测：已有集总压力图的仿真业务上，公开仓没有同类实现；可借鉴的是「元件端口上的压强与流量、腔体持有压力」；不适合搬连续场或粒子法，也不适合把传输线延时求解器换进去。对照过不等于要改实现。花费低于一次普通方案审。

## 1. 问题

复杂系统里让 AI 直接改代码，常见困境是：问题很大、对话很长、改一处坏一处，却说不清这一轮到底解决了没有。对话越长，越容易同一错误改很多次，人也越难叫停。

没有事先写清的过关标准时，现场往往变成下面这样：

- 没先看本项目代码，按别的项目习惯改，对不上接口；
- 原因只留在聊天里，下一轮仍按旧判断改；
- 自动检查过了，或日志里出现某几个字，就当成现场已经正常；
- 同一问题连续多轮小改，越改越乱；
- 为过某一个演示，写下只适用于该场景的特例。

目标是三件事同时成立：

1. **把真问题做完**：范围和过关标准事先写清，做完能对照复查。
2. **难问题上能停**：同一做法反复失败就要停、换思路，并记下此路不通。
3. **系统还能继续用**：失败记录是过程，产品仍要能交付、能维护。

一句话：用写得清楚、事后能复查的约定，让 AI 改复杂系统时少原地打转、该停时能停、做完能收尾。它是流程秩序，用来减少空转；效果好不好，仍以人看见的现象为准。

## 2. 定位与预期

多数同类工具聚焦在代码本身：补全、审查、扫描。本文讨论的工具多管一层：**开发流程的秩序**。需求对齐 → 方案确认 → 执行 → 验收 → 复盘 → 止损，串成可重复、可度量的闭环；失败热度可以自动升档，把过程数据变成规则。代码仍由人与助手一起写；业务好不好仍由人看软件里的现象。本工具保证每一轮改动有据可查、该停能停、做完能收尾。


| 它能帮你                 | 人仍然要做的                  |
| -------------------- | ----------------------- |
| 事先写清「改什么、怎样算过关」      | 打开软件，确认现象是否真修好          |
| 反复改不好时停下来换做法，并留下记录   | 盯着难问题，决定何时换思路           |
| 不懂开发的人也可用固定说法参与      | 第一次先说初始化，从「项目经理 + 需求」开工 |
| 解压后说 `项目经理 初始化` 即可试用 | 为本项目补路径和测试清单            |


若体验与预期不符，常见原因是：把它当成「装上就全自动」的工具，或还没说初始化就让 AI 直接改代码。适合对内正式用、对外试用。打安装包时不会带上各项目业务文档；对方说 `项目经理 初始化`，回归场景由本项目后补。

## 3. 方法

机制清单见下文 §3.5。本节只讲**为什么这么走**。入口与安装 → [README.md](./README.md)。

### 3.1 同一入口，按规模分粗细

人始终用同一句话开工：说明要解决什么，或看到什么现象。改动规模决定走哪条车道；车道定下来之后，才改仓库。小改可以缩短前置步骤，过关标准和改完要验这两项仍然保留，因为没有它们就无法对照复查。

需求说不清时（模糊、大需求、多次澄清仍分歧），助手应一次一问把设计分支问完再动笔。问完仍由人拍板。

### 3.2 事先写清怎样算过关

过关标准必须能对照复查：改什么、留下什么、怎样算修好。标准写在改代码之前。标准要能证伪：写明用哪份数据、哪个字段来判定失败。这样机械校验绿的时候，人仍然知道自己在验哪一句。

每个需求单独一个文件夹。结束时把文件夹从「进行中」挪到「已签收」或「未通过」，这样下一轮能看见结局。验收不过时，先看上一轮有没有留下有用进展，再决定保留或撤掉。

### 3.3 反复失败则停，记下此路不通

同一手法反复失败，就触顶封存、换路，并把「此路不通」留下，避免下一轮用同一判断再改一遍。失败记录是过程数据，用来下次换思路；产品仍然要能交付。

### 3.4 验收以人看见的现象为准

要不要算修好，以人在软件里看到的现象为准。可重跑的断言（单测、打包校验、日志关键词）用来加严同一句过关标准。黄金场景与手测照常。物理是否合理、产品允不允许，要写进项目说明或任务说明，让助手按已写的口径做，而不是临场发明。

这些不是功能清单，是护栏——每一条都对应真实改码里已经踩过的失败模式。日常使用不必背这张表；助手按岗执行。入口与安装仍看 [README.md](./README.md)。

| **回归索引 + 热度** | 上次挂过的模块/文件再次改动时，**已在标准车道**则加强审（L1.5；命中热度取较高档：方案审 L3 / 双轮 CR）；不单独把快/直通抬进标准。过去的失败抬高审核线，不靠人记 |

## 5. 讨论：思考碰撞试验

普通方案审是单向隔离：一方写、另一方审。思考碰撞是加审：先对齐前提；再用不同模型一轮「盖」对「拆」；后两轮只对残留分歧投票，不再重写方案。用来在人点名时多找一层洞。日常任务走普通方案审，因为碰撞大约要多花两到三倍时间。读到规程，说明助手知道怎么跑；要真正开跑，需要人点名。

### 5.1 设置

前两次打的是**同一份**尚未实施的流程方案：第一次用旧手续（两链全量审查 → 互审 → 第三窗再裁）；发现写回之后，再用现行薄碰撞打第二次。第二次的对象已经带上第一次的写回，所以两次结果用来看「写回后还有没有洞」，用来比较新旧手续需要另做对照。

第三次换了一份**从未进过方案审、也从未碰撞过**的流程稿，问的是：没有普通审垫底时，薄碰撞自己能不能用。前三次都是流程方案。

## 6. 讨论：逆链试验

怎么跑：模拟面先有一次归档倒走；再对**同一份**模拟切片做异模型并联两次，互不读对方产出。业务方案面两次都是：一次骨架倒走，再换模型抽检四元组；抽检保持原选型；后一次倒走不读前一次存档。三次模拟加两次业务都是骨架倒走、只标撑住或断裂。对照史外置。两次用来看「同一份稿倒走是否复现」，启用手续补完前后用来看「先把手续做完再倒走」是否撑得住。

## 7. 讨论：分歧标注试验

普通方案审是单向隔离：一方写、另一方审。分歧标注是同一助手、同一轮里显式写出至少两条视角推理链，先写推理再下结论，再对照有没有实质分歧；有则入队待澄清，无则结束。用来把「是不是在吵同一件事实」写成可入队的一条。日常走普通方案审；要开多视角，需要人点名。已隐去项目业务细节与窗号。

### 7.1 设置

对象是同一份模拟切片：只建只读真源和零行为诊断，并把总现象写进失败标准以便对照，不接后续执行。目的是练对照手续。

怎么跑：同一助手单轮产出两个视角的独立推理链（一个盯物理现象能不能被本步观察，一个盯本步范围许不许可去修总现象），先链后结论，再列表对照。有实质分歧则写成一条可入队的标注并进待澄清队列；无则字面结束。本轮只开分歧标注。两次视角用来看会不会真吵；对照表用来决定是否入队。

花费无账单，只能自估：单轮同模型，对照本身约 0.3–0.5× 普通 L1.5（粗估输入一万 token 内、输出两千内）；整步把记录写进本文之后，仍明显低于一次逆链倒走加抽检，也低于一次思考碰撞全链路（碰撞自估六到八万）。表里的倍数是自估，用来比较手续轻重。

## 8. 讨论：项目典故试验

项目典故是日常手续：写方案前扫设计模式症状表的「触发症状」，命中则写强制选型句，未命中则字面写不采用。用来把玩法症状翻成可执行选型。三次问的是：玩法说明不写模式名、新对话没有点名上下文时，助手会不会自己对上已有词条——一次按结构落地，一次按禁用边界改走直调，一次在 **使用与入表拆开** 之后采用并按配方新建。已隐去项目业务细节与窗号。第 5–7 节是点名才开的加审；本条是日常检查项的留痕。

### 8.1 设置

对象是另一仓库的需求：人只写玩家能看见的现象和跟法，玩法里只写看见什么、怎么跟。新开对话，不带上一轮点名。主窗派策划只给需求路径、车道，以及「扫症状表」；选型由策划对照症状表自己落盘。实现按选型改代码；人以软件里看见的现象验收后签收。这样设，是为了看症状表自己能不能把玩法翻成选型：主窗只给扫表任务，结论由策划对照症状落盘。

第一次的跟法句是按触发症状锁过的。仓里已有同类局部通知口可复用。第二次换了一份「做成之后出现一次贴外形的视觉、两种操作共用一套，按次数出现」的说明，手续相同。

第三次仍在另一仓库、新开对话，手续相同。跟法是若干操作成功后同一地点各出现一次短时水花，后一次盖前一次，按次数出现。该仓当时没有已验证的适配器入口可复用。先按改规则前的条文写不采用并落一次性私有播放；再按改规则后的条文（**使用与入表拆开**）写强制选型句采用「特效适配器」，并按「出现 / 改指向 / 适配 / 每帧」结构配方新建第一份门；结构按配方做。前后对照的是技能条文：同一份玩法，改条文前后各跑一窗，用来看使用规则改完之后助手会不会按配方新建。

| --- | -------------------------------------------------------------------- | ------------------------------------------------------- | --------------------------------------------------------------------------------------------------------- |

### 8.3 评价

这三次回答的是：不写模式名、不靠对话史点名时，症状表能不能把玩法翻成可执行选型并约束结构。第一次按压缩包落地。第二次按禁用边界改走直调。第三次在使用与入表拆开之后，当时没有验证入口，仍对上词条并按配方新建；漏接线要在交审时核调用点。它验证的是词条表这一手续：症状怎么翻成选型、禁用边界怎么拦住误套、没有现成入口时怎么按配方做第一份。

**还要不要再试。** 同一跟法句再开一窗，多半还是同一结论。第二次「按禁用边界走直调」与第三次「对上并新建」是两面，分开记。若要验证「命中后按压缩包落地」另一词条，须换一份会踩中触发症状、同时落在适用范围内的说明；第三次已覆盖「当时没有验证入口仍按配方新建」。

**读数口径。** 前后对照的是技能条文。第一次仓里已有同类通知口；第二次仓里已有直调外观；第三次新建了门。玩法按次数出现。跟法句是按触发症状锁过的。第一次词条禁用边界写「只通知一个固定对象则直调」，跟法要求「口能被别处接」，所以走了通知口。第二次「已知唯一对象、一次性改外观」，所以走了直调。第三次靠改规则后的「使用与入表拆开」，才从「不采用」转为「采用并按配方新建」。

细节留在该次任务文件夹里，本文不点名业务窗或现场原文。

### 8.4 这三次实际验证了什么

第一次：把玩法症状翻成已有词条，并按压缩包约束结构（局部通知、成对解除、回调保持主题状态、只保留这一套通知），人测通过。第二次：禁用边界拦住误套，走直调，人测通过。第三次：使用与入表拆开后，按出现/改指向/适配/每帧新建第一份门，人测通过；漏接线要在交审时核调用点。三次留痕回答「症状表这一手续能不能用」。通用典故 **一错不二犯** 管的是坑与结构分开记、同一错不再犯；**使用与入表拆开** 管的是症状命中即可按配方落地、有锚点才登记。两词各管一层。

## 9. 讨论：外仓对照试验

接到需求后先去网上搜类似项目、整仓下载再写方案，容易变成按别人的接口改自己的仓库。外仓对照把这件事收成点名才开的薄手续：先读本仓库，再最多列三个公开仓（许可、像在哪、不像在哪），浅克隆只进临时目录，只抽结构，禁止复制进业务目录。用来在人点名时看「公开仓有没有可借鉴的拆法」，不是拿外仓当开工图纸。日常不搜、不下载。读到规程，说明助手知道怎么跑；要真正开跑，需要人点名。已隐去本仓库符号、路径与业务场景。

### 9.1 设置

对象是一份**已有集总压力图**的仿真业务：压力在元件或腔上，边上有通断，不是网格里每个格子都有压强。人先问公开仓有没有气体/液体压力模拟，再收窄范围（不限定某引擎），再问哪个适合借鉴，最后点名启用对照。启用后先核对本仓库已有符号，再短清单，再浅克隆一个许可明确的仓到临时目录读核与元件库，不改业务代码。

短清单三类：集总元件仿真、管网水力、连续场或粒子法。只克隆集总那一类（核与元件库许可允许再分发）。另两类只读公开页。目的是练「粒度对得上才抽结构、对不上就写不选」。

花费无账单，只能自估：浅克隆加读核与若干元件头文件，明显低于一次普通 L1.5 方案审，也低于一次思考碰撞或逆链倒走加抽检。

### 9.2 结果


|     | 第一次（点名启用）                                                                                                                                                |
| --- | -------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 怎么跑 | 先读本仓库；短清单 ≤3；浅克隆一个许可明确的公开仓到临时目录；只抽结构；写「不选照抄」                                                                                                             |
| 对象  | 已有集总压力图的仿真业务；对照公开的集总液压/气动元件库，以及只读的管网水力与连续场/粒子法                                                                                                           |
| 花费  | 无账单；低于一次普通 L1.5；临时克隆不入库                                                                                                                                  |
| 打到  | 公开仓**没有同类实现**。可借鉴一层：元件有端口，端口上同时有压强（强度）和流量，腔体类持有压力状态，通流类按两端压计算流量，阀是通流不是泵。不适合：连续场或粒子法（粒度是空间场，不是元件图）；管网水力（节点压守恒像，但缺气相腔与边上的相态通断）；集总仓自带的传输线延时、特征阻抗、体积公式与孔口方程组 |
| 味道  | 对照能把「像在结构、不像在求解器」分开写；对照过没有变成改实现                                                                                                                          |


### 9.3 评价

这一次回答的是：手续能不能跑、会不会误把连续场或整套求解器当成可抄对象、抽出来的结构能不能对上本仓库已有粒度。单次能跑通：短清单三类分清了，克隆只进临时目录，业务目录未改。公开仓没有同类实现，这一句写进了结论，没有假装「网上都有现成的」。外仓对照是外源结构对照：便宜，用来点名时抽一层；落地仍用本仓库已有符号。一次点名是演练记录。对照过不等于要改实现。

**还要不要再试。** 同一份已有集总压力图再对照，多半还是「抽端口与腔压、不抄传输线」。若要再试，换一份本仓库**没有**集总图的绿场能力，看提示条件会不会出现、短清单会不会仍挡住连续场。

**还要不要继续优化规程。** 「提示 ≠ 启用、加载 ≠ 启用、禁止复制、临时目录、选型须有不选照抄」已经够用。继续抠句式收益很小。要盯住的假结果：未点名却写成已对照，或对照后把外仓类名写进改动清单。

### 9.4 它实际起什么作用

它把「网上有没有类似实现」做成可停的检查：先本仓库、再短清单、再只抽结构。粒度对不上就写不选，并写负向代价（换求解器会冲掉已有通断与驱动量）。模型按格式输出清单和落点；洞察要留下，靠下次默认仍先读本仓库、禁止把外仓当图纸。

## 10. 与常见说法的差异

网上「用 AI 写代码」的说法大多收敛到同一条骨架：先想清怎样算完成 → 先写方案再动手 → 边做边验 → 做完对照验收。本文也在这条骨架上，但有三处别处少见的做法，都来自真实使用中踩过的坑：


| 做法   | 多数说法                | 本文                                  |
| ---- | ------------------- | ----------------------------------- |
| 交付闭环 | 聊完、diff 看完就算完       | 每个需求一个文件夹，结束时挪到「已签收 / 未通过」，下一轮能看见结局 |
| 确认方式 | 反复问「你理解了吗」再开工       | 一次确认：回「准」= 理解 + 方案 + 开工全部确认         |
| 文档形态 | 大多是给 AI 的规则文件或单篇技巧帖 | 一份文档同时承担：新人导读、预期对齐、流程概要、真实使用记录      |


## 11. 怎么用这些结论

- 要不要算修好，以人在软件里看到的现象为准；机器检查用来加严同一句过关标准。
- 物理是否合理、产品允不允许，写进项目说明或任务说明，让助手按已写的口径做。
- 确认后可以少打断你；每步仍要验收，因为过关标准写在改代码之前，改完仍要对照。
- 换项目：说 `项目经理 初始化`；回归索引可后补。
- 思考碰撞：人点名时加审。四次实测是演练记录。前三次打流程方案；第四次打正在执行的业务实现，打到的仍是同类洞。正文已隐去业务窗号与现场现象。
- 逆链：人点名时倒走。一次归档加同稿并联两次、再加同一份改码前业务方案两轮（准入未过 → 手续合格后再倒走），是演练记录。模拟面打到总现象与本步连不上；业务方案面先停在启用准入，合格后再倒走则设计连接撑住。标通过须完成抽检（含用户抽检兜底）。正文已隐去业务窗号与现场现象。
- 分歧标注：人点名时多视角。本次是演练记录（同一模拟切片、当时为单轮同模型两视角）。现行技能已改为两隔离槽 + 对照由派发方写。打到一条非阻塞级分歧：本步零行为与总现象失败标准连不连得上；动作面保持原实现。正文已隐去业务窗号与现场现象。
- 项目典故（设计模式症状表）是日常检查。三次跨仓库实测：一次对上已有词条并按结构落地，一次扫到后按禁用边界改走直调，一次在使用与入表拆开后对上词条并按配方新建；均人测后签收。拿它判断症状表能把玩法翻成选型。漏接线要在交审时核调用点。正文已隐去业务窗号与现场现象。
- 外仓对照：人点名时才搜公开仓、浅克隆到临时目录、只抽结构。一次实测：已有集总压力图时公开仓没有同类实现；可借鉴端口上的压强与流量、腔体持有压力；不抄连续场、粒子法或传输线延时求解器。对照过不等于要改实现。正文已隐去本仓库符号与业务场景。
