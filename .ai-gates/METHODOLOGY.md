# AI 辅助复杂系统开发方法论

想了解「为什么这么设计」时再看本文。动手改代码、第一次接入仓库 → [USER-GUIDE.md](./USER-GUIDE.md)。机制清单与工作流 → [README.md](./README.md)。版本见 [VERSION](skills/VERSION)。

本文是给人读的论文，不是给助手的操作手册。助手不必默认读本文，也不必把全文贴进对话。

## 摘要

用 AI 改复杂系统时，失败很少是因为「不会写代码」，更多是因为范围说不清、过关标准事后才补、同一条错路改很多轮、机器检查绿了就被当成现场已经好了。本文主张：在代码补全与审查之外，再管一层**开发流程的秩序**——事先写清改什么、怎样算过关；按改动规模走不同粗细的步骤；失败反复出现时强制停下来换思路；验收权留在人看见的现象上。

这套约定已在仿真业务、流程自改、同事其他主题、另一光学仓库，以及非技术角色按口令推进的小游戏上用过，并能做完收尾。它不是严格对照实验，不能证明「用了就变好」。思考碰撞（非常规、异模型互审）三次实测表明：新手续能跑通；写回后仍能挖洞；换一份从未审过的流程稿，第一次碰撞也会打到同类洞（失败句抓不到、字段未钉、验收与清单不同句）。花费约普通方案审的两到三倍，不构成「已经元认知、所以该常开」。元认知要靠把「假设了什么、不知道什么、定级凭什么」写进日常检查，而不是加轮次、加模型。

## 1. 问题

复杂系统里让 AI 直接改代码，常见困境是：问题很大、对话很长、改一处坏一处，却说不清这一轮到底解决了没有。对话越长，越容易同一错误改很多次，人也越难叫停。

没有事先写清的过关标准时，现场往往变成下面这样：

- 没先看本项目代码，按别的项目习惯改，对不上接口；
- 原因只留在聊天里，下一轮仍按旧判断改；
- 自动检查过了，或日志里出现某几个字，就当成现场已经正常；
- 同一问题连续多轮小改，越改越乱；
- 为过某一个演示，写下只适用于该场景的特例。

目标不是多建几个文件夹，而是三件事同时成立：

1. **把真问题做完**：范围和过关标准事先写清，做完能对照复查。
2. **避免在很难的问题上空转**：同一做法反复失败就要停、换思路，并记下此路不通。
3. **系统还能继续用**：失败记录只是过程，不等于产品只能靠不断修漏洞过日子。

一句话：用写得清楚、事后能复查的约定，让 AI 改复杂系统时少原地打转、能停下来换思路、能把事情做完——**不是**装上就自动变强的万能药。

## 2. 定位与预期

多数同类工具聚焦在代码本身：补全、审查、扫描。本文讨论的工具多管一层：**开发流程的秩序**。需求对齐 → 方案确认 → 执行 → 验收 → 复盘 → 止损，串成可重复、可度量的闭环；失败热度可以自动升档，把过程数据变成规则。它不替人写代码，也不替人判断业务，而是保证每一轮改动有据可查、可停可撤、做完能收尾。

| 它能帮你 | 它不能替你 |
| --- | --- |
| 事先写清「改什么、怎样算过关」 | 代替你确认软件里现象是否真修好 |
| 反复改不好时停下来换做法，并留下记录 | 保证每次一次改对、完全不用人盯 |
| 不懂开发的人也可用固定说法参与 | 不配置本项目、不从约定入口开工，仍稳定好用 |
| 解压安装包后自己填项目说明即可试用 | 把别人项目里的路径、测试清单直接带走就用 |

若体验与预期不符，常见原因是：把它当成「装上就全自动」的工具，或还没做首次配置就让 AI 直接改代码。适合对内正式用、对外试用。打安装包时不会带上各项目业务文档，对方须自己填写项目说明。

## 3. 方法

机制清单见 README「机制表」，流程主线见 README「工作流」。本节只讲**为什么这么走**。

### 3.1 同一入口，按规模分粗细

人始终用同一句话开工：说明要解决什么，或看到什么现象，而不是直接让 AI 改。改动规模决定走哪条车道；没有这一步，不应直接改仓库。小改可以缩短前置步骤，但不能跳过「怎样算通过」和「改完要验」。

需求说不清时（模糊、大需求、多次澄清仍分歧），助手应一次一问把设计分支问完再动笔，而不是甩一屏问题或直接猜。问完仍由人拍板，不替人决定。

### 3.2 事先写清怎样算过关

过关标准必须能对照复查：改什么、不改什么、怎样算修好。标准写在改代码之前。若标准本身不可证伪——例如只禁止某种做法、却不说明用哪份数据、哪个字段来判定失败——后续的「机械校验」可以一直绿，问题仍在。

每个需求单独一个文件夹。结束时必须离开「进行中」：有据可查、可停可撤、做完能收尾。验收不过时，先看上一轮有没有留下有用进展，再决定保留或撤掉。

### 3.3 反复失败则停，记下此路不通

同一手法反复失败，不应无限小补丁。止损的意义是：触顶就封存、换路，并把「此路不通」留下，避免下一轮用同一判断再改一遍。失败记录是过程数据，不是产品只能靠修漏洞过日子的证明。

### 3.4 机器检查通过，不等于业务上可接受

要不要算修好，以人在软件里看到的现象为准。可重跑的断言（单测、打包校验、日志关键词）是加严，不是替代。断言绿了，现场仍可能不对；黄金场景与手测照常。物理是否合理、产品允不允许，要写进项目说明或任务说明，不能靠助手临场发明。

## 4. 使用记录

已在多条线上用过并能做完收尾。不是概念稿，也不是严格对照实验。

| 类型 | 说明 |
| --- | --- |
| 复杂仿真业务 | 大量真实任务：有的已验收通过，有的未通过后主动停住换路 |
| 改进协作方式本身 | 用同一套约定改流程说明，多批已归档 |
| 同事其他主题 | 同实验室其他功能也有按文件夹管理的产出 |
| 另一光学项目 | 发展过程中在别的仓库用过 |
| 非技术角色 | 模拟经营类、2D 跳跃类游戏开发；后者全程由财务背景、无开发经验者按口令推进 |

**效果数据**（最近一次截取：2026-08-06；实时口径以过程打点日志为准；已隐去项目业务细节）

| 指标 | 数值 | 含义 |
| --- | --- | --- |
| 机器打点记录 | 17 条 | 2026-07-22 起；结构化指标仅覆盖此口径 |
| 首过率 | 77%（10/13） | 一次通过验收即收口（机器记录内） |
| 平均返工轮 / 平均验收失败 | 0.15 / 0.15 | 交审级修复轮 / 验证失败次数（机器记录内） |
| 止损打点 | 2 条 | 机器记录内的止损叫停 |
| 任务窗总量 | 约 120 个 | 含测试夹具与示例 32 个 |
| 业务窗 | 64 个 | 主业务域 62 + 另 2 个问题域；跨多域、非单人产出 |
| 止损叫停回退 | 17 个 | 触顶封存 9、提前停或重定界 8 |
| 验证失败 | 5 个 | 事先写的过关条款未过 |
| 方案否决 | 3 个 | 此路不通、方案性否决后放弃 |
| 流程/自改窗 | 24 个 | 用同一套约定改进流程本身 |

止损链在真实执行里的样子：失败窗里 17 个是按规则叫停（同一手法反复失败至触顶则封存换路，不是无限小补丁）；另 3 个方案性否决也由止损或复议收口。失败根因集中在少数高难度现象域（业务细节未公开）。多轮原因分布：语义 2、假设 2、范围 1、其他 1。数据可复现：仓库内过程打点汇总脚本。

**诚实边界**：结构化指标只覆盖有打点的 17 条；任务窗与失败窗为目录统计（含示例，未逐窗核对）。非严格对照实验——只能说明「在这套约定下做过并收尾」，不能证明「用了就变好」。

## 5. 讨论：思考碰撞试验

普通方案审是单向隔离：一方写、另一方审。思考碰撞是非常规手续：先对齐前提；再用不同模型一轮「盖」对「拆」；后两轮只对残留分歧投票，不再重写方案。常规任务不启用。加载规程不等于启用。

### 5.1 设置

前两次打的是**同一份**尚未实施的流程方案：第一次用旧手续（两链全量审查 → 互审 → 第三窗再裁）；发现写回之后，再用现行薄碰撞打第二次。这不是随机对照，不能把「第二次打到新洞」直接读成「新手续全面优于旧手续」——第二次的对象已经不是第一次的原文。

第三次换了一份**从未进过方案审、也从未碰撞过**的流程稿，问的是另一面：没有普通审垫底时，薄碰撞自己能不能用。三次都是流程方案，不是从零当场写方案，也不是业务实现。

花费无账单，只能自估：大约都是普通方案审的两到三倍（第二、三次全链路粗估六到八万 token）。

### 5.2 结果

| | 第一次（旧） | 第二次（薄碰撞·同稿写回后） | 第三次（薄碰撞·未审新稿） |
| --- | --- | --- | --- |
| 怎么跑 | 两链全量 → 互审 → 第三窗再裁 | 先对齐前提；一轮盖/拆；后两轮只投票残留 | 同第二次 |
| 对象 | 一份尚未实施的流程方案 | **同一份**，且第一次发现已写回 | **另一份**，从未方案审、从未碰撞 |
| 花费 | 约 2–3 倍普通方案审 | 同量级（粗估 6–8 万 token） | 同量级（无账单） |
| 打到 | 3 条挡验收：2 条清单能抓，1 条是表对不齐 | **新的** 2 条挡开工：条款与清单字面互斥；「机械校验」未点名字段 | 6 条采纳：失败句抓不到自报；窗键未钉日志字段；清单加行不在验收；手工红线被脚本绿顶替；停点不在验收；口径多写了未验收的源。另 2 条需人拍板 |
| 味道 | 主要在改定级 | 前提对齐；分歧收窄；需人拍板的点标出 | 未审稿第一次就打到与第二次同类的洞；无翻转 |

第一次互审改定级，没有新的「我不知道」。第二、三次前提对齐都未截断，无模型在对立双方之间翻转。第三次说明：这类洞不是第一份稿写坏了才有，未审的流程稿也会在「条款不同句 / 字段未钉 / 脚本绿盖不住手工红线」上翻车。

### 5.3 评价

作为「新手续能不能用、写回后还有没有洞、换一份未审稿还能不能打到」——成功。作为「已经元认知、所以该常开」——不成立。花费未明显变便宜。仍不证明每个方案都值得付这溢价。

**还要不要再试。** 流程方案这一面可以停：同稿再撞、再换一份同类流程短窗，多半还是同一类洞。若要再推广，剩下的是从零写方案，或真实业务实现——不是继续打磨规程。

**还要不要继续优化规程。** 碰撞格式形态已够用，继续抠句式是边际递减。第三次再次标出了需人拍板的点（第三条路与多数并列），说明归并规则能用。真正增值仍是把打到的洞回灌进普通方案审的默认检查项，让下次不必付约三倍花费。

**能不能增加元认知。** 三次都没有自发的「我不知道」。加轮次、加模型、换一份未审稿，都不会提高元认知，只会加价。要加深，靠碰撞中强制上报「我不知道」、定级绑证据、以及回灌。常规仍不启用。

### 5.4 它算不算元认知

算半步，不是已经实现。半步在于：它把「我们可能没站在同一前提上」做成了可截断的手续，并把「这条判断凭什么升级」绑到可复查的锚上。还不算元认知本身，是因为模型并没有因此获得自我知识——它只是被要求按格式输出；「我不知道」不会自动出现；洞被撞出来之后，若不变成下次默认会做的检查，昂贵的洞察就只存在于这一次对话里。

## 6. 与常见说法的差异

网上「用 AI 写代码」的说法大多收敛到同一条骨架：先想清怎样算完成 → 先写方案再动手 → 边做边验 → 做完对照验收。本文也在这条骨架上，但有三处别处少见的做法，都来自真实使用中踩过的坑：

| 做法 | 多数说法 | 本文 |
| --- | --- | --- |
| 交付闭环 | 聊完、diff 看完就算完 | 每个需求一个文件夹，结束时必须离开「进行中」挪到「已签收 / 未通过」，不能只改状态字 |
| 确认方式 | 反复问「你理解了吗」再开工 | 一次确认：回「准」= 理解 + 方案 + 开工全部确认，不单独加一轮「复述理解」 |
| 文档形态 | 大多是给 AI 的规则文件或单篇技巧帖 | 一份文档同时承担：新人导读、预期对齐、流程概要、真实使用记录 |

## 7. 边界

- 自动检查通过，不等于业务上可接受。
- 物理是否合理、产品允不允许，要写进项目说明或任务说明。
- 确认后可以少打断你，但每步仍要验收。
- 换项目：带走通用说明，单独填配置。
- 思考碰撞非常规，默认不启用；三次实测不是对照实验，且都停在流程方案。
- 不必把本文整篇贴进对话。助手日常从 README 与 USER-GUIDE 开工即可。
