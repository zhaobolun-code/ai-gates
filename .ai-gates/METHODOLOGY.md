# AI 辅助复杂系统开发方法论

给新人、试用者看：先弄清「为什么要用」。
动手改代码 → [USER-GUIDE.md](./USER-GUIDE.md)。
第一次接到仓库或解压安装包 → [USER-GUIDE.md](./USER-GUIDE.md)。  
助手不必默认读本文。版本见 [VERSION](skills/VERSION)。

## 一句话

用写得清楚、事后能复查的约定，让 AI 改复杂系统时少原地打转、能停下来换思路、能把事情做完——**不是**装上就自动变强的万能药。

## 定位：AI 编码的项目经理

多数同类工具聚焦在「代码本身」——补全、审查、扫描；ai-gates 多管一层：**开发流程的秩序**。需求对齐 → 方案确认 → 执行 → 验收 → 复盘 → 止损，串成一个可重复、可度量的闭环；失败热度自动升档，把过程数据变成智能规则。它不替你写代码、也不替你判断业务，而是保证每一轮改动有据可查、可停可撤、做完能收尾。护栏机制清单见 [README.md](./README.md)「机制表」。

## 试用前请先对齐预期

| 它能帮你 | 它不能替你 |
| --- | --- |
| 事先写清「改什么、怎样算过关」 | 代替你确认软件里现象是否真修好 |
| 反复改不好时停下来换做法，并留下记录 | 保证每次一次改对、完全不用人盯 |
| 不懂开发的人也可用固定说法参与 | 不配置本项目、不从「项目经理」入口，仍稳定好用 |
| 解压安装包后自己填项目说明即可试用 | 把别人项目里的路径、测试清单直接带走就用 |

若体验与预期不符，常见原因是：把它当成「装上就全自动」的工具，或还没做首次配置就让 AI 直接改代码。

## 要用它解决什么

复杂系统里让 AI 直接改代码，常见困境是：问题很大、对话很长、改一处坏一处，却说不清这一轮到底解决了没有。对话越长，越容易同一错误改很多次，人也越难叫停。

目标不是「多建几个文件夹」，而是：

1. **把真问题做完**：范围和过关标准事先写清，做完能对照复查。
2. **避免在很难的问题上空转**：同一做法反复失败就要停、换思路，并记下此路不通。
3. **系统还能继续用**：失败记录只是过程，不等于产品只能靠不断修漏洞过日子。

## 没有它时常见情况

- 没先看本项目代码，按别的项目习惯改，对不上接口；
- 原因只留在聊天里，下一轮仍按旧判断改；
- 自动检查过了或日志里出现某几个字，就当成现场已经正常；
- 同一问题连续多轮小改，越改越乱；
- 为过某一个演示，写下只适用于该场景的特例。

## 怎么做（概要）

机制护栏清单见 README「机制表」——这里只讲日常怎么运作、为什么这么走。

人始终用同一句话开工：说明要解决什么或看到什么现象。助手先判断改动大小，再决定简单改还是先写方案；没这一步不应直接改仓库。

常见路径：写清改什么、不改什么、怎样算通过 → 有人看方案 → 你确认可以做 → 改代码 → 再检查 → 按约定验收。小改可以缩短前面步骤，但不能跳过「怎样算通过」和「改完要验」。

每个需求单独一个文件夹。实现只按当前任务写明的范围来。要不要算修好，以你在软件里看到的现象为准；若本步只改说明文档、不改业务程序，可以用另一助手按清单核对，结论仍要你过目。

验收不过时：先看上一轮有没有留下有用进展，再决定保留或撤掉；认识变了先改写「现象说明」，再开下一轮。确认可以开工后，助手可以连续改和检查，但**每一步都要验收**。事情真正结束时，文件夹应挪到「已签收 / 未通过」等位置，不能只改几个字却还停在「进行中」（一般由助手处理，你不用手挪）。

## 使用记录（摘要）

已在多条线上用过并能做完收尾；不是概念稿，也不是严格对照实验。

| 类型 | 说明 |
| --- | --- |
| 复杂仿真业务 | 大量真实任务：有的已验收通过，有的未通过后主动停住换路 |
| 改进协作方式本身 | 用同一套约定改流程说明，多批已归档 |
| 同事其他主题 | 同实验室其他功能也有按文件夹管理的产出 |
| 另一光学项目 | 发展过程中在别的仓库用过 |
| 非技术角色 | 模拟经营类、2D 跳跃类游戏开发；后者全程由财务背景、无开发经验者按口令推进 |

多轮原因分布：semantic 2 / hypothesis 2 / scope 1 / other 1。数据可复现：运行
`powershell -File .ai-gates/scripts/summarize-pipeline-outcome.ps1`（由
`append-pipeline-outcome.ps1` 打点）。**诚实边界**：结构化指标只覆盖有打点的 17 条；

只能说明「在这套约定下做过并收尾」，不能证明「用了就变好」。

适合「对内正式用 + 对外试用」。打安装包时**不会**带上各项目业务文档；对方须自己填写项目说明。

## 和网上常见说法有什么不同

网上「用 AI 写代码」的说法大多收敛到同一条骨架：先想清怎样算完成 → 先写方案再动手 → 边做边验 → 做完对照验收。本文也在这条骨架上，但有三处别处少见的做法，都来自真实使用中踩过的坑：

| 做法 | 多数说法 | 本文 |
| --- | --- | --- |
| 交付闭环 | 聊完、diff 看完就算完 | 每个需求一个文件夹，结束时必须离开「进行中」挪到「已签收 / 未通过」，不能只改状态字 |
| 确认方式 | 反复问「你理解了吗」再开工 | 一次确认包：回「准」= 理解 + 方案 + 开工全部确认，不单独加一轮「复述理解」 |
| 文档形态 | 大多是给 AI 的规则文件或单篇技巧帖 | 一份文档 = 新人导读 + 预期对齐 + 流程概要 + 真实使用记录（四合一） |

## 新人建议阅读顺序

1. 本文 → 2. [USER-GUIDE.md](./USER-GUIDE.md) → 3. 需要时再查细则。

```text
项目经理
[需求 / 现象 / 报错]
```

新项目第一次：`项目经理 初始化`。

## 边界

- 自动检查通过，不等于业务上可接受。
- 物理是否合理、产品允不允许，要写进项目说明或任务说明。
- 确认后可以少打断你，但每步仍要验收。
- 换项目：带走通用说明，单独填配置。
- 不必把本文整篇贴进对话。
